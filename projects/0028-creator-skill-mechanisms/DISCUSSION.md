# 我们对创作 Skill 的理解

这份记录整理本轮讨论的判断，不把第三方仓库说明当作已验证效果。

## 从个人体感出发

用户认为，每个人对口播和文风的体感不同，Skill 仍要自己摸索、创建；第三方的主要价值是参考。我们认可这个判断在语气、审美和表达偏好上的适用性，同时补充：检查清单、样本使用方法、工具流程与记录机制也可能直接复用，不需要全部从零。

## 与直接生成公平比较

直接生成若已经得到同样的目标、材料、真实样本、规则和工具，打包成 Skill 不保证质量更高。需要分别看它是否减少重复交代、漏项、改稿和操作，以及是否增加了原本没有的资料和执行能力。

## 从能力标签改为具体流程

最初只列“内容诊断”“个人口播”“表达润色”，无法判断实际能力。用户要求改为“输入是什么 → 做了什么处理 → 输出是什么 → 对我们的价值”。因此每仓库选择一条口播相关代表流程，明确交付物：审稿报告、预测与复盘记录、逐字稿、逐镜脚本和润色正文，不混作成片结果。

## 把价值解释到内部原理

“少返工、能省时”仍不足以说明为何有效。用户进一步要求说明内部如何约束并达到目标。最终重点变为：

1. dbs-script-flow 用固定维度逐段检查，问题绑定原句，改稿保留标记，限制修改范围。
2. cheat-on-content 在结果出现前保留预测，原预测不覆写，规则更新需历史重评与默认独立审核。
3. ray-kb 先读真实样本，录后对照；结构检查脚本核对章节、格式与母稿指纹。
4. space-video-script 用逐镜字段把台词与画面、时间和转场对应起来，约定后续交接。
5. ra-人话 先列事实、立场等保留项，再用禁用表、正反例和复扫约束改写。

## 区分执行强度

文字指令规定模型应该做什么，仍可能被遗漏。程序检查只能检查已编码的项目，并依赖运行环境。结构、哈希或字段检查通过，不代表事实真实、风格适合或内容有效。人的试读、实际录制和连续作品反馈仍要保留。

## 我们怎样使用

先直接做作品，亲自修改，同时留下生成稿与实际使用稿；提炼反复有效的样本、规则和检查步骤，再沉淀自己的 Skill。外部仓库提供候选方法，我们决定取舍。审美和语气用自己的样本，机械步骤验证后复用，规则随新作品更新。

图中是机制与价值示意。本次没有安装运行完整上游工作流、验证流量预测或完成创作质量对照实验。
